# 前端 Goal 模式说明

## 目标

这份文档用于记录本轮前端改造时采用的目标导向工作方式，以及当时确立的视觉和执行约束。

它更像一份“前端改造原则说明”，不是交付结果文档。

如果要看当前交付状态，请优先阅读：

- [frontend-project-closeout.md](D:\java\project\docflow-ai\docs\frontend-project-closeout.md)
- [goal-execution-roadmap.md](D:\java\project\docflow-ai\docs\goal-execution-roadmap.md)

## 1. 核心目标

本轮前端改造的核心目标是：

- 把当前前端逐步收敛为偏企业后台风格的统一界面
- 保留现有业务逻辑、路由和接口契约
- 优先修复最影响观感和一致性的高频页面
- 用成熟组件替换粗糙原生控件
- 每轮改动后都保持页面可构建、关键测试可复用

## 2. 核心方向

本轮改造不再延续“概念稿 / 漂浮卡片 / 过度留白”的视觉路线，而是统一转向更克制的后台系统风格。

设计方向：

- 更像企业后台，不像营销页或展示稿
- 信息层级清楚，减少大面积空洞 Hero
- 表格、筛选区、表单行是核心结构
- 颜色收敛，减少发光、渐变、玻璃感和悬浮感
- 间距紧凑但不拥挤，优先可读性和稳定感

## 3. 非目标

本轮不优先做这些事情：

- 不重写业务流程
- 不改后端接口语义
- 不先做完整设计系统再开始改页面
- 不优先抽象复杂主题平台或通用能力引擎
- 不为了“设计感”牺牲系统感和信息密度

## 4. 硬约束

- 不随意改业务逻辑，只做必要的表现层整理
- 能用 `Element Plus` 的地方，优先不用粗糙原生控件
- 组件替换后要补最基本的样式收口，不能只停留在“能用”
- 改完页面后至少验证 `frontend` 下的 `npm run build`
- 命中已有页面级测试时，要同步修复或更新对应测试
- 如果遇到明显范围扩张或视觉分歧，再暂停确认

## 5. 视觉规则

### 页面结构

- 页头要紧凑，不做过大的标题区
- 筛选区和列表区要属于同一套骨架
- 表单优先按“标签 + 控件 + 动作区”的后台结构组织
- 统计信息只保留必要数量，避免碎卡片堆积

### 控件

- 输入框、选择器、按钮尺寸偏企业后台尺度
- 选择器和输入框尽量统一高度、圆角、边框和 focus 状态
- 尽量避免原生 `select` 的粗糙展开体验
- 避免过大的圆角、过重阴影和过厚 padding

### 语气

- 以白、灰、蓝为主
- 文案优先中文后台语境，减少突兀英文标签
- 状态色只用于表达状态，不用于制造装饰感

## 6. 当时的优先顺序

本轮改造按以下顺序推进：

1. 工单高频页面
2. 创建 / 编辑类表单
3. 详情页与列表页壳层统一
4. 知识库相关页面
5. 侧边导航、顶栏和公共壳层
6. 单测债与文档收尾

## 7. 工作方法

每次推进时遵循以下节奏：

1. 先判断当前页面最丑、最不协调的部分是什么
2. 优先修结构问题，再修控件问题，最后补局部样式
3. 只做当前页面必要改动，不无边界蔓延
4. 完成后跑构建
5. 命中已有测试时同步验证测试
6. 用简短结论记录这一轮改了什么、下一步该改什么

## 8. 完成定义

一个页面可以暂时视为“收敛完成”，需要满足：

- 视觉方向已脱离原先的概念稿感
- 结构更像成熟后台页面
- 表单和列表控件不再明显粗糙或突兀
- 页面可正常构建
- 已知受影响测试已同步处理

## 9. 当前意义

这份文档的价值现在主要体现在两点：

- 帮助理解这轮前端为什么会沿着“后台收敛”方向推进
- 给后续维护者一个判断标准，避免又回到早期展示型视觉路线

如果后续继续做前端演进，建议把它当作“历史改造原则”，而不是新的任务清单。
